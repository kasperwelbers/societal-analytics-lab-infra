    OIDC provider comparison

    Evaluation

    This page is the evaluation behind our choice of Keycloak (November 2026): the comparison, the hands-on test checklist, and what we found. The decision and its reasons are on the Decisions page. Some use cases below were dropped later: a shared provider for other teams' servers (use case 3, now the lab's own idp), and client registration by others (use cases 2 and 6).

    It is only about the provider that the lab runs itself: our software works with any provider that meets the provider requirements.

    What we need

    Use cases

    # Use case Description
    1 Lab authentication Login for the lab's own infrastructure: our AmCAT and AnnoTinder servers, and the AuthWall in front of services without their own login (Whisper, Ollama). Ideally from the same user pool as use case 3, but isolated if that is more secure.
    2 Easy client registration Users who host our software can register their server themselves, and get a client ID, client secret and redirect URI configuration.
    3 Identity provider One shared pool of users, with one account for all servers that use our provider. We control everything: users can't manage other users or add login methods.
    4 Isolated OIDC providers Power users (e.g. a research group) get their own pool of users, and fully manage it themselves: users, login methods, 2FA settings and account recovery.
    5 Migration Teams can move to another OIDC provider later (see the Migration guide).
    6 Self-registration Users (not power users) can create an account themselves. Client registration starts with limits (e.g. a maximum number of clients) that we can increase.
    7 Consent and SSO Single sign-on across all servers, but users consent once per host before a server receives their data. AmCAT and AnnoTinder on the same host count as one host, so one consent covers both.

    Requirements

    These follow from the use cases and the Authentication standard.

    • Consent screen. When other people register clients, the provider must ask users before sharing their data with a client they haven't used before. Without consent, any registered client receives the name and email address of a signed-in user, without the user being asked. That is acceptable only when we register every client ourselves.
    • Tenant isolation. For use cases 1 and 4, users in one pool must not be able to sign in to (or be signed in to) clients of another pool, and this must be enforced by the provider, not by the configuration of each client.
    • Self-service client registration with limits, ideally via the standard (OAuth 2.0 Dynamic Client Registration, DCR), so that our registration page or tooling stays small.
    • The provider requirements of our standard: email_verified, a 2FA signal (amr or acr), and step-up (max_age, auth_time). Ideally also the option to request 2FA (acr_values), so that users without a second factor are asked to set one up.
    • Little maintenance, and an active project with a clear future.

    Per provider

    Keycloak

    The most complete fit for our use cases, and the most battle-tested. Its main cost is complexity: Keycloak has many settings, and a misconfiguration is a bigger risk than the code itself. We manage that by keeping the realm configuration in files in this repository, which Keycloak imports itself (see step 7 of the installation guide), so that it is reviewable and reproducible.

    • Realms give us strong isolation on one server: a realm for the shared pool, a realm for the lab, and a realm per power user.
    • Consent is stored per client. The consent screen is skipped only when the user already approved everything the client asks for.
    • Client registration policies can force consent for every self-registered client, so a registered client can't skip it.
    • Step-up: levels of authentication (acr) can require 2FA on request. Our servers must still check the returned acr themselves, because providers don't always enforce what was requested (see CVE-2026-97176 in Provider support).
    • Deployment: one container and PostgreSQL. start-dev is for local testing only; production needs start with a database, hostname and reverse proxy settings (see the production, reverse proxy and hostname guides).

    Authentik

    Our current lab provider. Simpler than Keycloak, with good forward auth and a built-in consent flow. It covers the identity provider case, but not isolated pools for power users, and it can't request 2FA on demand. It also depends on a small team.

    • Consent: a built-in explicit consent flow, configurable per application.
    • Isolation: one installation is one pool. Multi-tenancy existed for a while, but has been removed.
    • DCR: present in the current source code, including an option to force the authorization flow (e.g. explicit consent) for dynamically registered clients. Its availability in releases and editions needs to be verified.

    ZITADEL

    ZITADEL works well when we register every client ourselves, and the users are ours. It is not suitable for the two other roles we need:

    • Identity provider (use case 3). ZITADEL has no consent screen. A user who is signed in is passed to any registered client without being asked, and the client receives their name and email address. When other people can register clients, users have no say in which clients receive their data. So ZITADEL can't be our identity provider for servers that others run, unless we vet every client.
    • Tenant isolation (use cases 1 and 4). ZITADEL organizations separate user management, but they don't isolate users: whether a client accepts users from other organizations depends on the configuration of that client's project, which is managed by the project's owner. The instance admin can't enforce isolation for all organizations. So separate pools for power users, or for the lab, would each need a separate ZITADEL instance.

    One client per host

    AmCAT and AnnoTinder hosted together on the same host can use the same client ID and client secret. This gives users one consent per host, which matches who actually receives their data: the operator of the host, not the software.

    • Register the redirect URIs and post-logout redirect URIs of both applications on the client.
    • Each application still has its own session (its own session cookie), and logging out is still per application.
    • Both applications share the client secret. Rotating the secret means updating both.
    • Tokens have the same audience for both applications. This is not a problem, because our applications use their own session cookies and don't accept each other's tokens.
    • A client has one back-channel logout URL. Our applications don't use back-channel logout; if that changes, each application needs its own client again.

    The Authentication standard describes this as an option.

    Keycloak test checklist

    To be done on a test machine, before migrating anything. Mark items as done, and add findings below each section.

    Basics

    • Run Keycloak locally with start-dev, create a realm and a confidential client (authorization code flow with PKCE).
    • Log in to a test application, and check the ID token: email_verified, auth_time, amr.

    Consent (use cases 3 and 7)

    • A new user logging in to a client with consent required sees a consent screen.
    • The consent is remembered: a second login to the same client shows no consent screen.
    • AmCAT and AnnoTinder sharing one client on host A: one consent covers both.
    • A client on host B asks for consent again.
    • A silent login (prompt=none) for a user who did not consent returns an error (interaction_required), not a token.
    • Users can see and revoke their consents in the account console (Applications → Remove access); the next login asks for consent again.

    Client registration (use cases 2 and 6)

    • Register a client via DCR with an initial access token that allows 2 registrations. A third registration is refused.
    • A client registration policy forces consent for every dynamically registered client.
    • A registered client can't turn off consent afterwards (via the client update endpoint).
    • Trusted hosts or redirect URI restrictions work as expected.
    • To verify: whether a policy exists that keeps new clients disabled until an admin enables them.

    Instead of DCR, apps were first registered through our own app registration site, which used the admin API with narrow rights. Since idp is only for the lab's own servers, our admins create the clients, and a client policy turns on consent and PKCE and refuses unsafe redirect URIs (tested, see step 8 of the installation guide). The DCR items above are therefore no longer needed.

    Users and 2FA

    • Self-registration with required email verification.
    • amr for password, password plus TOTP, password plus passkey or security key, and a passkey alone: pwd, and pwd + mfa (see the findings for the passkey alone).
    • Step-up: max_age triggers a new login, and auth_time is updated (tested with max_age=5).
    • Requesting 2FA with acr_values: a user without a second factor is asked to set one up. Our server checks the returned acr. (Not used: our setup signals 2FA in amr, and our software does step-up with max_age.)
    • Users can't add login methods (e.g. link other accounts) unless we allow it.

    Sessions

    • SSO session lifetime of 30 minutes (idle and maximum).
    • Behaviour on a shared computer after the session ends.

    Isolation (use cases 1 and 4)

    • A second realm with a delegated realm admin. That admin can't see or change anything in other realms (tested, see step 4 of the installation guide).
    • A user signed in to one realm is not signed in to another realm.

    Migration (use case 5)

    • Export a test realm with users, import it into a fresh Keycloak. Logins work, and user IDs are unchanged.

    Operations

    • Production setup with start, PostgreSQL and our reverse proxy (hostname and proxy headers): see the Keycloak installation guide.
    • Realms set up from files with Keycloak's own import (see step 7 of the installation guide).
    • Upgrade from one 26.x release to the next.
    • Backups of the database, and a restore test.
    • oauth2-proxy in front of a service without its own login (the AuthWall).

    Findings

    Tested with Keycloak 26.8 (locally, with the realm configuration of the installation guide):

    • 2FA flows: mandatory 2FA (with OTP setup for users without a second factor) and optional 2FA both work with Keycloak's built-in conditions, also after Google or GitHub (post login flows). A post login flow in which nothing runs counts as failed: the optional flow needs an "Allow access" step.
    • Copying a flow in the admin console keeps the old flow name in "Condition - sub-flow executed". The copy then silently skips (or repeats) the 2FA step. Hence check-realms.py.
    • amr needs a reference value (pwd, mfa) on each authenticator. Right after setting up OTP during a login, amr contains only pwd (the OTP was set up, not used). After Google or GitHub, amr has no pwd.
    • Account linking in a realm without self-registration: a Google or GitHub login for an unknown email is refused; for an existing account, the user confirms by email first.
    • The admin API refuses tokens of a service account without the default client scope kc-admin-api (401), and checks the roles in the token: with fullScopeAllowed off, a service account loses its admin roles.
    • Delegating clients to their owners works with fine-grained admin permissions (v2): a user sees and edits only their own client in the admin console. But managing those permissions requires manage-realm, which is too much for an automated registration site.
    • Client policies can enforce consent, PKCE and redirect URI rules for changes made by a specific role. The redirect URI rule can only allow http://localhost by allowing http:// in general (our site checks the rest). An empty post logout redirect URI attribute is refused.
    • Client updates keep attributes that are left out; clearing one needs an empty value. Searching clients by attribute is disabled by default.
    • Emails: Keycloak sends the verification email on the first visit to the "verify your email" page (not on the registration form itself), and the password reset email when "forgot password" is submitted. Both only when client_id in the URL is the app of the login, which makes a limit per app in the proxy possible. Resending a verification email right away sends nothing (Keycloak throttles it). With email verification on, Keycloak 26.8 lets new users choose their password only after verifying their email.
    • Email address as username, and changing it: the required action Update email is off by default; without it, users edit their address directly and it is only verified afterwards. With it, the address (and the username) changes only after the new address is confirmed, and the user keeps the same sub, also when they log in with an external provider. The account console only shows the Update email button when Edit username is allowed; the email field stays read-only, and a direct change through the account API is ignored. Changing to an address of another account is refused ("Username already exists"). In a realm without an email server, Update email together with email as username makes accounts without an email address (the bootstrap admin) unable to log in with the admin CLI ("Account is not fully set up").
    • Passkeys: a passkey or security key works as a second factor after the password (amr: pwd + mfa). With "Enable passkeys" (webAuthnPolicyPasswordlessPasskeysEnabled), users can also sign in with only a passkey, but that happens in the step with the password form, so out of the box amr is only pwd, and a flow with mandatory 2FA still asks for OTP. Our flows add a condition ("a passkey was used") that skips the OTP steps and records mfa (tested in all three realms). The account console then offers a passkey twice: under two-factor authentication and under passwordless sign-in.
    • Re-login (max_age) shows the username as text and asks only for the password.
    • Forgot password: Keycloak's default reset credentials flow ends with "Reset OTP", which asks the user to set up a new authenticator app (the old one is kept, with the option "Remove none"), and logs the user in right after the new password, without the second factor (force-login only applies to users from external user stores). So an inbox is enough to get in, and to add an authenticator app. Our flow drops "Reset OTP", and asks users with a second factor for it right after the email link, before the new password; in lab, users without one set up OTP in the same go. Then the user is logged in (tested in lab and idp). (A first version turned force-login on, which makes the user log in again after the new password; that worked but was clumsy for new members.)
    • Required actions run in priority order, not in the order the flow asks for them: by default "Configure OTP" (54) comes before "Update password" (57), so a new member set up the authenticator app before choosing a password. We changed the priorities.
    • Recommending 2FA without forcing it: a required action in a login flow can't be skipped. An app can send the user to the setup with kc_action=CONFIGURE_TOTP: that page has a Cancel button, and the app gets kc_action_status=cancelled or success back (tested). That is the place for a "set up 2FA" recommendation, e.g. on a landing page.
    • Themes can change the texts, CSS and images of the login pages, the account console and emails without changing page templates: a theme with only theme.properties (parent=keycloak.v2) and messages_en.properties. The login header is the message loginTitleHtml, rendered as (sanitized) HTML, so a logo and subtitle need no template; footer.ftl is Keycloak's own place for a custom footer. The account console takes logo, favIcon and styles in theme.properties. Realm overrides (localizationTexts) apply to all theme types, so a changed label (e.g. "Email") also turned up outside the login pages; in a login theme, it stays on the login pages.
    • Partial import of users gives them no roles (not even the realm's default roles), and needs username even with email as username. Without default-roles-<realm>, the account console fails with 401 ("Sorry, an unexpected error has occurred").
    • Recovery codes: the required action Configure OTP has an option Add recovery codes: after setting up an authenticator app (at the first login, or later in the account console), the user sets up recovery codes too. There is no such option after adding a passkey. A recovery code works as a second factor (Try another way), each once (tested).
    • Login action timeout applies to each page of the login, not to the login as a whole: with 20 seconds, 25 seconds on one page restarted the login, while 15 seconds on each of two pages worked (tested).
    • Linking Google or GitHub to an existing account (idp): Keycloak shows "Account already exists", and the user confirms by a link sent to the address, or by the account's password and second factor ("Try another way"). In the latter case, the second factor is asked twice, only this first time: once to confirm the link, and once by the post login flow (tested). After linking, the second factor is asked once.
    • Secrets and realm admins: the file vault keeps secrets out of the database, backups and the admin console (the console shows the reference, e.g. ${vault.smtpPassword}). But a realm admin can reuse the reference: after pointing the realm's SMTP host to another server, Keycloak sent the SMTP password there; a new login provider with ${vault.googleClientSecret} as its secret sent the Google client secret to its token URL. Secrets stored in the database are better protected: the console masks them, and changing a provider's token URL without entering the secret again is refused ("Client secret must be re-entered ..."). Keycloak's SMTP password has no such protection, so email goes through a relay that holds the provider's password, and Keycloak has none to give away (all tested).
    • Realm import: Keycloak's own import (--import-realm) only creates realms that don't exist yet, and only fills in its defaults for parts that are missing from the file entirely: a file with only our own flows gets none of the built-in flows, and a file with one client scope gets none of the default scopes. So the realm files are complete exports (a default realm plus our changes). master is imported too on a new installation, before the temporary admin is created, whose password must then meet the imported password policy. Placeholders for missing environment variables are imported as text. (We first used keycloak-config-cli, a third-party tool that applies changes to existing realms; it needs an admin client with a secret on the server.)
